## 1. Impact of Comments on LLM Comprehension of Legacy Code (`2506.11007v1`)

- **Question/method:** Does comment quantity or accuracy change LLM understanding of legacy code? Four model families (Claude-3, Llama 3, Mixtral, GPT-4) answer custom multiple-choice quizzes about one open-source IBM z/OS assembler module (Walmart's L8WAIT). Two assembler SMEs helped create the quizzes. Each model/condition was run three times.
- **Support:** Comment-rich code generally led to higher quiz scores than no comments in this one module. When all comments were replaced by unrelated/inaccurate material, average performance on the original advanced questions fell from 73% with accurate comments to 61% with inaccurate ones. Some models also produced fabricated explanations that followed misleading comments.
- **Counterevidence and threats:** Replacing 20% of the comments with inaccurate text had negligible effect for three of four models; the sharp drop required completely inaccurate comments. With no source code supplied, the models still scored 75% on the advanced quiz, suggesting possible benchmark/code memorization. This is one module, four systems, a bespoke MCQA proxy and only three repeated runs; the authors say the answer-option positions were not randomized and identify this as future work. The source therefore does not establish that comment density generally improves program comprehension.
- **Sections checked:** RQs and design; six L8WAIT variants and four quizzes; model setup/repeats; results for comment density, 20%-incorrect and fully incorrect comments; conclusion/future work.
- **Version/status:** arXiv v1, submitted 2025-04-23; comments say preliminary findings. [Primary record](https://arxiv.org/abs/2506.11007).

## 2. Dynamic Stability of LLM-Generated Code (`2511.07463v1`)

- **Question/method:** Does functional correctness capture differences between correct programs with different algorithms/runtime behavior? The authors propose Static Canonical Trace Divergence (SCTD), Dynamic Canonical Trace Divergence (DCTD), and an exploratory ratio, Behavioral Expression Factor (BEF), based on opcode distributions. They evaluate 11 commercial/open models on BigO(Bench)'s 311-problem test set and CodeContests validation/test splits. Each model–problem configuration has five generated solutions at temperatures 0, 0.7 and 0.95; GPT-3.5 receives a denser temperature sweep.
- **Support:** Across many model settings, the paper observes algorithmic and runtime-trace diversity even among solutions passing public tests. Its reported temperature sweep usually finds higher pass@1 accompanied by larger SCTD/DCTD, illustrating a plausible correctness-versus-stability trade-off. This is a useful reason to retain efficiency/behavior measurements alongside pass@k.
- **Counterevidence / scope:** The authors explicitly acknowledge only five generations per configuration, Python-only evaluation, and dependence on the benchmarks' test-suite coverage; BigO test cases lack sufficient asymptotic cases for deeper behavioral analysis. Thus SCTD/DCTD/BEF are candidate diagnostics, not validated proxies for production incidents or algorithmic risk. The result does not establish a universal monotonic temperature law.
- **Sections checked:** Metric definitions and BEF interpretation; benchmark/model setup; generation protocol; main model/temperature tables and figures; threats to validity; conclusion.
- **Version/status:** arXiv v1, submitted 2025-11-07. [Primary record](https://arxiv.org/abs/2511.07463).

## 3. Lost in the Flow with Code Talkers: Unveiling the Instruction-Tuning Tax of Large Language Models in Code Tasks (`2606.08676v1`)

- **Question/method:** How do base and instruction-tuned code models differ across developer interaction modes? The study compares Qwen2.5-Coder (1.5B–32B) and DeepSeek-Coder (1.3B–33B) variants across fill-in-the-middle (FIM), completion, and instruction-following tasks. It also fine-tunes Qwen2.5-Coder-7B with the public Magicoder pipeline and audits intermediate checkpoints.
- **Support:** In the sampled benchmark suite, instruction-tuned models often lose on FIM but gain on some tasks with natural-language/docstring guidance. For example, several Qwen/DeepSeek SAFIM and infilling comparisons regress; ClassEval completion often improves. The checkpoint study is non-monotonic, and grouped averages show a small FIM decline and task-dependent completion changes. This suggests that “code capability” is not one outcome and training effects depend on the interface and task.
- **Counterevidence / boundary:** Results differ by model family, benchmark and size; there are explicit exceptions (e.g. some larger DeepSeek infilling settings do not show a statistically significant paired difference). The study's own threats include undisclosed pre/post-training corpora and possible benchmark contamination, just two model families, a smaller single-family Magicoder replication, function-level/offline tasks, and no user study of real IDE workflows. Do not convert its average trends into an inevitable instruction-tuning penalty.
- **Sections checked:** task/benchmark definitions; model families and paired comparisons; RQ1 tables and McNemar tests; sampled failure analysis; checkpoint trajectories; threats to validity and conclusion.
- **Version/status:** arXiv v1, submitted 2026-06-07. [Primary record](https://arxiv.org/abs/2606.08676).

## Targeted full-text follow-ups / counterevidence

### A. Testing the Effect of Code Documentation on Large Language Model Code Understanding (Findings of NAACL 2024)

The seven-page full text uses GPT-3.5/GPT-4 to generate unit tests for the 164 HumanEval functions under documentation variants. Ordinary comments did **not** significantly improve successful-test rate, though they did improve line coverage; random, wrong comments significantly harmed success/coverage. This pushes against a general “more accurate comments always improve correctness” interpretation and supports a more specific reliability distinction. It is a small Python/HumanEval study with a possible contamination limitation. Importantly, both authors are also coauthors of sampled paper 1, so this is chronological evidence from the same research group, not independent replication. [ACL Anthology primary PDF](https://aclanthology.org/2024.findings-naacl.66.pdf).

### B. Extending Fill-In-the-Middle with Instructions for Steerable Code Completion (`2509.24637v3`)

The full arXiv HTML and experiment tables were checked. IFIM separates an instruction segment in the FIM representation and fine-tunes two base code-model families using 122.9k mostly Python instruction/completion pairs synthesized with GPT-4.1. It improves instruction-conditioned scores on IHumanEval/IRepoMasterEval and largely preserves no-instruction completion; on Qwen-2.5-Coder, one IFIM ordering is an exception that regresses without instructions. A held-out set of 100 actual developer TODO/FIXME cases also favors IFIM on edit similarity and model-judge score. This is counterevidence to an *unavoidable* instruction-following/FIM trade-off: a task-matched objective can mitigate it. But the authors scope the evidence to two code families, synthetic training instructions, local context truncated to 20 lines, and do not test thousands-token repository context. [Primary full text](https://arxiv.org/html/2509.24637).

## Cross-paper synthesis and falsifiable opportunity

The more defensible conclusion is not “comments help” or “instruction tuning hurts.” Evidence suggests that **signal reliability and representation matter**: relevant comments can help on a targeted legacy-code quiz, irrelevant comments can mislead, and a benchmark-specific FIM format with an explicit instruction channel can recover capabilities that generic instruction tuning may trade away. Separately, pass@1 misses variation among correct solutions, but current stability metrics remain under-validated and test-suite dependent. These papers use different languages, tasks, models and metrics; their headline percentages are not directly comparable.

**Test:** evaluate matched base, generic-instruct and instruction-aware-FIM models on a leakage-resistant, multi-language suite crossing (i) no comment, accurate instruction, stale/incorrect comment and explicitly marked instruction, and (ii) local FIM, repo-context completion and command-style generation. Use multiple samples per item and measure task correctness, compile/test pass@k, boundary/format errors, runtime and asymptotic behavior on expanding tests, comment contradiction detection, and developer acceptance. Preregister model/backbone, training-data provenance, held-out repository cutoff and task-level analyses. The signal-separation hypothesis weakens if explicit marking gives no reproducible benefit over plain comments, or if stale comments do not change failures; it strengthens if accurate/marked instructions help while wrong/stale context is reliably rejected, without increasing runtime tail risk. This audit did not run that experiment and makes no novelty or prevalence claim.
