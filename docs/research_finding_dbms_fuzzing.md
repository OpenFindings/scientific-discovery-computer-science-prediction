# 研究发现：数据库逻辑错误 fuzzing 的“引导信号—真实 bug”评估缺口

发现日期：2026-10-11
状态：有文献证据支持的研究机会；不是已证明的新方法，也不是已完成的系统综述。
范围：数据库管理系统（DBMS）的逻辑错误测试，重点关注 SQL 生成/状态变异的引导信号。

## 大白话结论

现在有几类方法都能找到数据库 bug，但它们盯的“好信号”不一样：

- QPG 追求产生更多、更新颖、更复杂的查询计划；
- SQLancer++ 通过数据库反馈，逐渐少生成目标数据库不接受的 SQL；
- SQLaser 根据过去真实 bug 总结容易出错的 SQL 子句组合和代码调用链，再定向测试。

这些结果说明三种信号都可能有用，但现有论文没有在相同数据库版本、相同 oracle、相同机器预算、相同随机种子策略和相同去重/厂商确认标准下，把三者放进同一个对照实验。因此，不能根据各自论文里的 bug 总数判断哪个最好，也不知道这些信号是互补、冗余，还是只在某些数据库/错误类型上有效。

更具体的缺口是：论文报告的代理指标（计划新颖度、SQL 有效率、代码覆盖、触发用例数）与“每 CPU 小时找到多少个厂商确认且根因不同的逻辑错误”之间，尚缺少跨方法、跨数据库的校准研究。

## 原始论文证据

1. **QPG：计划新颖度及 bug 产出。** Ba 和 Rigger 的 [Testing Database Engines via Query Plan Guidance](https://arxiv.org/html/2312.17510) 在 SQLite、TiDB、CockroachDB 上实现 QPG。论文报告 53 个经开发者确认的新 bug，其中 28 个逻辑错误（§V，表 III）；QPG 在 24 小时计划覆盖对比中显著超过 SQLancer/SQLRight，且 bug 效率实验报告总计 17 个 unique bugs（§V-Q.2/Q.3，表 VII）。需要谨慎的是，logic-bug 去重采用 SQL 子句结构相似作为 best-effort 判据，而非所有根因均经统一的厂商修复提交验证；TiDB 和 CockroachDB 的部分计划实验因 crash 只运行到 6 小时（§V-Q.2）。论文另报告整体 bug-finding efficiency 提升约 2×，但这仍是其自身方法/基线/去重定义内的比较。

2. **SQLancer++：有效率反馈及跨数据库扩展。** Zhong 和 Rigger 的 [Scaling Automated Database System Testing](https://arxiv.org/html/2503.21424) 报告在 18 个 DBMS 上发现 196 个此前未知 bug、其中 140 个逻辑错误，180 个已修复（摘要、§6）。论文中“带/不带有效性反馈”的 bug 产出消融是在 CrateDB 上以 TLP oracle 运行 1 小时、5 次重复（§5.3，表 5）：平均分别得到 11.4 和 9.8 个 unique bugs；该去重/版本 bisect 个案研究只覆盖 CrateDB。SQLite/PostgreSQL/DuckDB 的 24 小时×10 次结果表明，有反馈时 SQL 有效率分别为 97.7%、52.4%、64.2%，无反馈配置分别为 24.9%、21.6%、24.6%（§5.4，表 4）。作者同时发现代码覆盖高不必然意味着逻辑错误更多：SQLancer++ 在 DuckDB 和 SQLite 分别发现了 SQLancer 漏掉的 10 和 3 个新 bug（§5.3）。这支持“不同引导信号可能探索互补区域”，但不等于验证了与 QPG/SQLaser 的正面对比。

3. **SQLaser：历史错误模式/调用链定向。** [SQLaser: Detecting DBMS Logic Bugs with Clause-Guided Fuzzing](https://arxiv.org/html/2407.04294) 从 SQLite、MySQL、PostgreSQL、TiDB 的 144 个既有逻辑错误归纳出 35 种子句模式，并将其对应调用链作为定向目标（§3）。论文在四个 DBMS 上报告 22 个 bug 实例、其中 4 个经研究者和厂商确认根因不同于已有 bug（摘要、§6.1）；SQLite 的 SQLaser/SQLRight 对照运行 60 天，且作者报告 SQLaser bug 发现时间约降低 60%（§6.2.1）。作者明确指出当前 oracle 不完整：MySQL 已汇总的 15 个历史错误中有 13 个由未集成的 PQS oracle 检出，这可能解释 SQLaser 对 MySQL 只覆盖 10 种模式中的 4 种（§6.1）。所以即便模式定向有效，oracle 选择仍会改变可见的 bug 产出。

## 从证据得到的判断

这是一个**评估缺口和可检验研究机会**，而不是“没人把这些技术放在一起”的新颖性证明。现有证据特别支持两点：

1. 代理指标不能互换：QPG 显著增加计划多样性；SQLancer++ 显著增加 SQL 有效率；但 SQLancer++ 也展示代码覆盖更高不一定找到更多逻辑 bug。
2. 真实 bug 产出高度依赖数据库、测试时长、oracle、去重规则和报告/确认流程。现有三个 headline 数字的预算跨度从 1 小时到 60 天，数据库集合和确认口径也不同，不能横向排名。

一个潜在的综合方法可以把这些机制视为不同层次：有效性反馈负责“让输入可执行”，计划新颖度负责“拓展数据库状态/执行计划”，错误模式定向负责“把预算投向易错交互”。这只是由现有工作推导出的假设，尚未被组合消融实验证明。

## 可证伪研究问题与实验

**RQ：** 在固定 oracle、数据库版本和 CPU 小时预算后，SQL 有效性反馈、查询计划新颖度、历史逻辑错误模式定向是否各自增加厂商确认且根因不同的逻辑错误产出？它们组合时是互补还是冗余？计划新颖度/有效率能否预测此类真实 bug 产出？

**预注册假设：** 相比基础 SQLancer 配置，三种信号中至少一种会提升“每 CPU 小时厂商确认且根因不同的逻辑错误数”；组合配置的效果不必然等于单项提升之和。另行检验代理指标和真实 bug 产出的相关性，不把相关性当成因果机制。

**建议实验设计：**

- 选择至少 4 个开源 DBMS，覆盖 SQLite、PostgreSQL、DuckDB，以及一个 SQL 方言/实现差异较大的系统；固定并公开精确 commit。
- 采用可执行的因子实验：基础配置；有效性反馈开/关；计划新颖度反馈开/关；历史 bug 模式定向开/关。资源有限时先对 2×2（有效率×计划新颖度）做全因子，再在选定系统加入模式定向因子。
- 固定每格总 CPU 小时数、硬件、oracle 组合（并分 oracle 报告）、并发/实例数、输入约束和随机种子清单；至少 10 个独立 seed。进行平衡运行次序并记录崩溃/重启造成的可用测试时间。
- 主要结果：每 CPU 小时的厂商确认、根因去重逻辑 bug 数，以及 time-to-first-confirmed-bug。盲化 triage，按修复提交/根因证据合并重复报告，并公开争议项。
- 次要结果：可执行 SQL 比例、计划签名的新颖度、代码覆盖、触发用例数、oracle 分歧、每个 bug 的子句/调用链标签。分别评估这些代理指标对主要结果的校准与跨系统可迁移性。
- 用负二项/计数模型（或预注册的稳健替代方法）估计各主效应与交互效应，并报告系统分层结果、置信区间及失败/零发现运行；不要只报汇总平均数。

## 反证、风险与尚未完成的核查

- QPG 已做多系统、多次重复和组件敏感性分析；这削弱“QPG 自己的证据薄弱”的说法，但并不回答与 SQLancer++/SQLaser 在匹配条件下的比较。
- SQLancer++ 现有数据已表明反馈提高有效率且 CrateDB unique-bug 均值提高；所以“有效率是否会增加 bug 产出”并非空白。新研究必须将贡献定位在跨系统外部有效性、与其他信号的交互，以及统一厂商确认/根因去重的结局，而不能重新包装其单项反馈消融。
- SQLaser 的 60 天设置、定向目标和 oracle 组合与其他工作差异很大。必须优先复用公开代码和 artifacts，确认各实现可在同一版本依赖中复现；不能假设轻易可集成。
- 本次是从项目里 198,690 条词法候选元数据出发的定向文献核验，不代表已经逐篇阅读 198,690 篇论文。已核读三篇核心论文的公开全文，未完成全领域系统综述、正式新颖性检索或独立复现。
- 因此当前置信度：**研究问题存在：中等偏高；综合方法会有效：低；全局新颖性：未确认。**
