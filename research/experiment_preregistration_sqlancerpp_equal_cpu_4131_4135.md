# Preregistration: SQLancer++ feedback at matched cgroup CPU budget

- **Study ID:** `EXP-DBMS-FEEDBACK-EQUAL-CPU-4131-4135`; recorded 2026-10-14 UTC before any study-seed run.
- **Pilot basis:** Five previous fixed-cap arms used 4.76–5.13 cgroup CPU seconds. Two unused implementation smokes at seeds 4997/4996 verified the new stop wrapper; at 4.5 CPU seconds, 13 complete 200-attempt databases had printed rates in the feedback-on smoke. Neither smoke seed enters the analysis.
- **Question:** At a matched 4,500,000-microsecond cgroup CPU budget per arm, does feedback-on increase independently reproduced *distinct* SQLite 3.40.0/NoREC discrepancies versus feedback-off? Successful query pairs from completed databases are a secondary operational metric, not bug yield.
- **Source/build:** SQLancer++ commit `1405d4eb5b7af7a639717a47147bd89362558830`; JAR SHA, Docker image digest and SQLite version are validated/recorded. One CPU, 1 GiB memory, no container network, 200 attempts/database, max 100 databases safety cap, 45-second program timeout. Each arm runs alone inside its own container/cgroup and is stopped by `scripts/stop_at_cpu_budget.sh` polling `cpu.stat usage_usec` every 20 ms.
- **Fresh paired seeds:** 4131, 4132, 4133, 4134, 4135. Balanced shuffled first-arm flags from `random.Random(4131).shuffle(["on_first"]*2+["off_first"]*3)` give off-first for 4131/4132/4134 and on-first for 4133/4135. Freeze this order before outcomes. Both arms use the same seed; no seed replacement.
- **Counter gate:** A pair is complete only if both arms have a `cpu_budget` stop receipt, positive `usage_usec` delta at least 4,500,000 and no more than 3% above target, at least eight complete per-database rates representing integer successful counts out of 200 attempts, and SQLite version logs. Any failure remains in the denominator and is reported; no optional stopping.
- **Primary outcome:** Number of *distinct independently reproduced* NoREC mismatches per arm. Export potential failure logs/SQL traces under anonymized IDs, deduplicate identical SQL and database states without condition labels, rerun candidates against the pinned SQLite build, then unblind. An empty candidate set yields zero only if the complete logs were inspected. If independent reproduction cannot be performed, primary outcome is unresolved rather than zero.
- **Secondary outcome:** Total successful query pairs in fully completed databases before CPU stop. The interrupted database's partial attempts are excluded from both arms; report complete database counts, discarded partial query counts when available, actual CPU spend/overshoot, each paired difference, mean, and exact sign test. This secondary proxy cannot establish bug-finding effectiveness.
- **Interpretation:** Five pairs have low power for rare bugs and for two-sided sign testing (all same-sign gives p=0.0625). A null bug count is inconclusive, not evidence of equal effectiveness. Never claim Paper 3/Paper 4 validity or a general DBMS result from this run.
- **Command:** `python3.12 scripts/run_sqlancerpp_equal_cpu_campaign.py --source /private/tmp/sqlancerpp-source-1405d4e --output results/sqlancerpp_feedback_equal_cpu_4131_4135` followed by a separate raw-log analysis.
